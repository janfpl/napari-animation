Performance investigation and implementation plan — 2026-09-22

The highest-priority change is to remove repeated data loading and synchronous slab projection from GUI callbacks. Then accelerate the remaining array computation with Numba or CUDA. Raising overall CPU/GPU utilization is not the acceptance criterion: the GUI must keep responding while data is read, and obsolete requests must stop consuming resources.

This plan preceded the first implementation pass. See `docs/performance-initial-implementation.md` for the applied changes, real-file benchmarks and remaining work.
See `docs/performance-implementation-status.md` for the second implementation pass, current test evidence, and the items that remain open.

**Evidence and limits**

Inspected the application source, installed napari source, and the Python/configuration/documentation files from both supplied ZIPs. Reference source files were extracted into the workspace's `reference_repos` directory. This workspace is an unpacked source tree, not a Git checkout.

The accessible `.venv` has Python 3.13, napari 0.8.0, VisPy 0.16.2, NumPy 2.5.3, Dask 2026.8.0, and cachey 0.2.1. h5py 3.16.0 and Numba 0.67.0 were subsequently installed into this workspace environment for the first implementation pass. CUDA/CuPy remains unavailable there. This is not proof of which environment runs the user's existing GUI. Inspect that process's environment before selecting deployment dependencies.

Hardware inspection found 48 logical CPUs, approximately 255.8 GiB system RAM, and an NVIDIA GeForce RTX 3070 with 8192 MiB VRAM, driver 576.02. One busy logical CPU corresponds to approximately 2.08% aggregate CPU usage. The reported 2.5% is consistent with a mostly serial stage, but could also reflect I/O, lock waits, or GPU synchronization. A Task Manager GPU percentage does not identify the CUDA workload or diagnose a rendering limit; measure the relevant engines, memory pressure, transfers, and stage timings.

The Imaris ZIP includes `napari_imaris_loader/_tests/brain_crop3.ims` (102,586,476 bytes). It was inventoried but not used for the first benchmark. The subsequently supplied `D:\081926\single tile.ims` and Embryo8b `.ims`/`.lux.h5` files were decoded with h5py and benchmarked on bounded pyramid levels and small native-resolution regions. No live Qt freeze trace or CUDA speedup measurement is available yet.

The headless probe confirmed:

| Probe | Result | Meaning |
|---|---|---|
| Three unchanged `OrthoSlice.ensure_layer()` calls | Three backing-layer `data` events | Redundant data assignments reach napari; this is not just a suspected event cascade. |
| Prefetch a napari 0.8 multiscale image | `TypeError: list indices must be integers or slices, not tuple` | The current level selector returns `MultiScaleData` instead of a level array. Production `_warm()` catches and hides the failure. |
| `np.take` on a simple array-protocol source | One full-array materialization | A non-Dask array-like can be fully converted before selection. Dask dispatch can behave differently; this probe does not establish whole-volume reads for every backend. |
| Basic slicing of the same source | One slice request, no full-array materialization | Slice first, materialize or reduce second. |

Run `examples/performance_audit_probe.py` with the workspace Python to reproduce. It uses small arrays and `ViewerModel`, redirects its settings/cache into `.performance-audit`, and does not benchmark a Qt canvas, disk, or CUDA. Results are saved in `docs/performance-audit-probe-results.json`.

The user identified **Add scroll-through, Add slice-sweep, Snap view, and selecting another keyframe** as the slow interactions. A second probe exercised those exact controller paths, in that order, with one small Dask-backed volume and one section, switching to XY before the remaining operations. Screenshots were stubbed; real GUI listeners may add further work. Counts describe this reproducible scenario, not universal counts for every scene:

| Controller action | `ensure_layer` calls | 2D projection calls | Screenshot requests | `ViewerState.apply` calls |
|---|---:|---:|---:|---:|
| Snap XY (`capture=False`, as the GUI uses) | 1 | 1 | 0 | 0 |
| Add scroll-through | 11 | 8 | 2 | 3 |
| Add slice-sweep | 14 | 10 | 2 | 4 |
| Select first keyframe | 6 | 4 | 0 | 2 |

These counts make repeated work the first optimization target for the reported buttons. Even selecting one keyframe performed four projection calls in this setup. Accelerating each projection would help, but eliminating unnecessary projections also removes their reads, allocation and upload costs.

`add_scroll_through()` (`animation.py:478–534`) moves the live dims to each endpoint and captures two keyframes. `add_slice_sweep()` (`:536–588`) renders each endpoint and captures two keyframes. Capture performs a screenshot, and list/selection callbacks can restore frames again. `set_movie_frame_index()` (`:828–859`) applies the stored state, restores editable scene state, then calls `renderer.apply_working()` again. Selection and programmatic selection updates need a single navigation transaction with a reentrancy guard; the probe confirms repeated application, without attributing all repeats to one event emitter.

For these controls specifically, batch-insert two **detached endpoint snapshots**, update selection/timeline notifications once, display the final endpoint once, and fill placeholder thumbnails asynchronously from their exact saved states. Preserve insertion order, timing, active section position, final working state and existing capture semantics. Separate adopting a selected snapshot into the editable model from rendering it, so selection produces one accepted render request. The Snap buttons already pass `capture=False`; their delay must be addressed in dims transitions, source rebinding, projection and native rendering, not by removing a thumbnail they never request.

The installed napari `ScalarFieldBase.data` setter resets level/thumbnail state, updates dimensions, and emits a data event without an identity early exit. This substantiates the repeated-binding concern. It does not establish how many seconds each assignment takes on the user's file.

Enabling native asynchronous slicing will not move this plugin's explicit `_apply_2d()` NumPy work off the GUI thread. Do not rely on the reference reader's late `os.environ['NAPARI_ASYNC']='1'` assignment after settings/viewer creation.

**CUDA and Numba opportunities**

| Operation | Preferred initial approach | CUDA decision |
|---|---|---|
| Axis-aligned max/min/mean slab projection | Basic slice and bounded streaming reduction; compare NumPy against explicit Numba output-pixel/row `prange` kernels with `nogil=True`, `parallel=True`, `cache=True`. | CuPy reduction is a small first prototype. Retain selected-level volume or frequently reused chunks on device; download only the projected 2D result. Use a fused custom kernel only if profiling justifies it. |
| Preview pyramid construction | Shifter-style streaming sums; Numba parallel XY reduction; reduce successive compatible levels without rereads. | Batch GPU work and retain intermediates. Benefit depends on transfer/compute balance; existing pyramids should be reused first. |
| Future oblique 2D reslicing | Explicit feature addition with a numerical oracle; parallel independent output pixels and fused interpolation/projection. | Strong candidate for a fused CuPy RawKernel or maintained NVIDIA Numba CUDA backend. Current transformed/oblique 2D rejection is intentional; do not silently change it while optimizing. |
| Contrast/histograms | Metadata or bounded coarse sampling off the GUI thread; cache per source/channel. | Useful when data is already device-resident; usually not worth a full-volume upload just for initial contrast. |
| Video resizing/encoding | Move resize and diagnostics off GUI thread; preserve ordered bounded writer. | NVENC may improve encode throughput if available in the chosen FFmpeg build. This is separate from CUDA projection and does not remove screenshots/readback. |
| HDF5 reads and decompression | Chunk-aware reads/cache; pipeline reader with compute; consider separate reader processes after measurement. | Ordinary h5py reads do not become GPU operations by installing CuPy/Numba. GPU decompression is a separate, filter-specific project. |
| 3D volume/plane rendering | Stop redundant uploads, limit resolution and duplicate textures; inspect VisPy/OpenGL timings. | Existing rendering is already GPU shader work. CUDA is not a drop-in accelerator for the Qt/VisPy renderer. |
| Camera/keyframe interpolation and small transforms | Keep lightweight CPU operations, avoid repeated application. | Too little arithmetic to justify transfer, launch, and synchronization overhead. |

Numba's CPU `parallel=True` does not automatically move work to CUDA. Use explicit independent output loops, and inspect parallel diagnostics: a generic axis reduction is not a guarantee of useful automatic parallelism. See [Numba parallelization documentation](https://numba.readthedocs.io/en/stable/user/parallel.html). For custom GPU kernels, check the maintained NVIDIA backend and its supported Python/NumPy/CUDA versions; the built-in Numba CUDA target is deprecated. See [Numba CUDA overview](https://numba.readthedocs.io/en/stable/cuda/overview.html).

The 8 GiB GPU is a shared rendering/compute resource. A 1024³ uint16 volume is 2 GiB before textures, dtype conversion, outputs, and workspaces; 2048³ is 16 GiB. Multiple plane layers can duplicate textures even when their Python arrays are shared. Start with a conservative device-cache cap (for example 1 GiB), reserve measured render headroom, and adapt to free memory. Use bounded host buffers and cache budgets rather than a fraction of total RAM alone. Keep CPU fallback and recover from out-of-memory without changing scientific results.

Compare complete worker latency, including HDF5 read, host-to-device transfer, kernel, device-to-host result, and GUI publication. Measure cold context/JIT startup separately from steady state and use CUDA events/synchronization correctly for timings. GPU kernels are asynchronous; plain host stopwatch measurements can be misleading. See [CuPy performance guidance](https://docs.cupy.dev/en/stable/user_guide/performance.html).

**Implementation sequence**

1. **Instrument actual interactions and establish the baseline.** Extend `perf.py` beyond export totals with request IDs, thread IDs, queue delay, read/materialize, projection, layer binding, GUI publish, screenshot and encode stages. Count data events, actual backend reads, requested/read bytes, cache hits, pending jobs and cancelled/stale results. Add a Qt heartbeat to measure event-loop gaps and a thread-stack capture during stalls. Profile XY/XZ/YZ/3D, add/toggle slice, thickness/projection edits, capture, timeline scrub, resolution changes and export. Record active Python/package versions, data shapes/chunks/compression, active level and disk location. Deliver a replayable benchmark and baseline JSON before claiming a speedup.

2. **Eliminate redundant work before adding compute backends.** Start with the four reported controls: batch endpoint construction/insertion for scroll-through and slice-sweep, and a single guarded keyframe-selection transaction. Snapshot adoption must not render the scene a second time. Give each section a binding signature: source identity/revision, selected pyramid level, and leading time/channel indices. Cache the selected array view so a fresh Dask view object does not force rebinding. Track transform and appearance separately. Only change `layer.data` when the binding changes; explicitly invalidate on source data events, including supported in-place edits followed by refresh. Do not resample for opacity/colormap-only edits. Reuse projection results for identical slab intervals. Avoid constructing/rebinding hidden 3D backing volumes just to render 2D. Pass known contrast limits at construction. Consolidate snapshot preparation/application and source visibility reconciliation. Preserve managed-layer IDs, authored visibility and keyframe semantics.

3. **Introduce cancellable asynchronous section requests.** Add a pure request planner and a compute service, for example `scene/section_request.py` and `processing.py`. The GUI freezes source identity/revision, level, time/channel selection, world-to-data transform, voxel interval, projection and quality into an immutable request. The worker only receives source handles/descriptors and arrays, never the live viewer. It returns array, affine, status and request ID. The GUI publishes only if the generation/source still matches. Bound active and pending work; replace obsolete queued requests rather than replaying every slider event. Use roughly 30–50 ms interactive coalescing and 250–350 ms idle refinement as initial tunable values. Preserve the last completed preview while loading. Cancellation is cooperative between bounded tiles; it need not interrupt an HDF5 call already in progress. Native slicing async configuration is a separate compatibility setting. Keep Qt objects and OpenGL operations on their owning GUI/context thread.

4. **Build one HDF5-aware data/cache path for interactive use and export.** Keep format readers separate from the renderer; the animation package should consume a source protocol or adapter rather than duplicate every file format. Implement native-chunk-aware basic ROI reads, byte-bounded LRU, and in-flight deduplication shared by preview, projection and prefetch. Cache keys include canonical source, internal dataset, time/channel, level, revision and chunk coordinate; projection keys also include interval, axis, projection, quality and sampling convention. Budget HDF5 raw-chunk caches, application caches and temporary arrays together. Begin with one reader lane plus compute overlap; benchmark 1/2/4 reader processes only where decompression is limiting. Each Windows spawned process opens its own read-only file and closes it after outstanding work ends; send descriptors, not h5py objects, and use bounded shared buffers to avoid copying whole volumes over IPC. Keep GUI imports out of spawned worker startup.

   h5py serializes HDF5 API calls with an interpreter-wide lock, even for different datasets/files. Increasing the current prefetch thread count is therefore not a general parallel-HDF5 solution. Independent read-only processes can read concurrently without requiring MPI; actual speedup depends on storage and decoding. See [h5py threading](https://docs.h5py.org/en/stable/threads.html) and [independent process reads](https://docs.h5py.org/en/stable/mpi.html).

5. **Add progressive resolution and repair prefetch.** Port the Imaris controller's coarse-preview and generation approach using global RAM/VRAM limits and stable IDs. Preserve physical transforms across levels and timepoints. Repair `MultiScaleData` selection, build prefetch from the same exact request planner as display, filter invisible/duplicate derived layers, and deduplicate by chunks rather than animation frame number. Bound lookahead bytes and pending futures; prioritize current interaction above speculative reads. Keep source handles and cache contexts alive until in-flight work finishes. Do not inspect viewer state in workers. Distinguish cancellation from backend failures in logs. Native napari multiscale 3D uses the lowest-resolution level; higher-detail 3D requires explicit level selection/staging, not an assumption that 2D zoom behavior applies. See [napari image API](https://napari.org/dev/api/napari.html).

6. **Add the Numba CPU backend, then benchmark optional CUDA.** Extract the exact projection calculation into a pure backend interface with NumPy as reference/fallback. Parallelize independent output tiles/rows, use axis-aware memory access, and avoid an unconditional contiguous copy of a huge slab. Preserve max/min dtype, NaN behavior, mean precision, half-open voxel-center intervals, edge/subvoxel behavior and output affine. Use safe accumulator widths; no `fastmath` until numerical requirements explicitly permit it. Compile representative dtype/axis signatures in a worker before enabling the fast path. Set an overall concurrency budget across Dask, Numba, readers and encoding; benchmark 1/4/8/16 compute threads rather than giving every pool 48 workers. Add optional CuPy with a real device/kernel probe and measured CPU/GPU crossover. Retain GPU data across nearby requests, use one controlled GPU work queue, and add pinned/double buffers only when transfer timing supports them. Select CUDA by end-to-end latency, not utilization or kernel-only speed. Package compatible optional extras in `setup.cfg` and CI; do not install unverified CUDA wheels into the user's existing GUI environment.

7. **Make export and thumbnails cooperate with the event loop.** Retain a synchronous API for scripts if needed, but use a GUI export controller with states: request data, await readiness, apply, await matching render, capture, enqueue, next. A full encoder queue pauses production without blocking the GUI. Resize, image diagnostics, encoding, muxing and verification run in workers where possible; screenshot/render stays with the Qt/OpenGL owner. A frame must wait for its own data and render completion, otherwise async loading can export stale images. Export uses exact requested quality and ordered frames, even when preview drops obsolete requests. Handle cancel/error cleanup asynchronously and restore the authored scene once. Defer thumbnails with a captured-state token so rapid subsequent edits cannot attach the wrong picture to a keyframe.

**Imaris and Luxendo details to preserve**

For IMS, retain the full reader shape/chunk contract until singleton axes are explicitly sliced in Dask; the supplied reader already fixes `squeeze_output=False`. Preserve resolution/time/channel identity, physical extents, padded-versus-logical shapes, and external-link targets. Avoid repeatedly reopening every level just to change resolution or contrast. Keep a persistent decompressed cache across interactions; the current animation Dask cache exists only during export.

For Luxendo, adapt discovery of flat `Data` and `Data_W_H_D` datasets plus the JSON `metadata` dataset. Translate factors from X/Y/Z names into Z/Y/X array order explicitly. Do not universally treat every `.h5` as Luxendo or every `.ims` as a self-contained file: manufacturer `main.ims`/BDV headers can reference multiple files. Separate header detection and link resolution from flat-volume scanning. Do not mistake a skipped header for a volume. Preserve independent X and Y spacing, units, channel/time labels and world transforms.

Shifter wraps Luxendo with Dask chunks `(64, -1, -1)`. That favors full-XY export slabs but is a poor default for interactive XZ/YZ/ROI access. A 64×4096×4096 uint16 logical block alone is 2 GiB. Read the real HDF5 chunk shape, align requests to it, and compare native blocks with small aligned groups. Basic slicing cannot eliminate native chunk decompression amplification; log physical chunks touched. For contiguous datasets, choose bounded logical tiles appropriate to the access pattern rather than pretending native chunks exist. If no useful pyramid exists, generate an optional versioned sidecar once in a background task using Shifter's streaming approach, then reuse it.

**Validation and completion criteria**

These are proposed acceptance gates, not measured outcomes:

| Area | Required check |
|---|---|
| GUI responsiveness | For the agreed workloads, target p95 GUI callback time under 50 ms and p95 heartbeat gap under 100 ms; separately report the maximum gap, preview latency and exact-result latency. Long disk reads must not stop input/cancel handling. |
| Avoided work | Unchanged binding/appearance operations cause zero backend voxel reads and zero source-data replacement events after warmup. Camera-only changes must not reload section data. |
| Reported buttons | One keyframe selection produces one final render transaction; endpoint creation inserts exactly two correct snapshots without synchronous endpoint screenshots. Repeat the supplied call-count probe plus Qt event integration tests; verify final selected frame, insertion position and sweep geometry. Snap remains capture-free. |
| Cache/prefetch | Revisit a slab within the declared cache budget without repeating backend reads; one producer for concurrent identical misses; bounded queued bytes/futures; no silent multiscale failure. Test time/channel/affine mapping and close while work is active. |
| Numerical parity | Compare NumPy, Numba and CUDA against the existing projection oracle across XY/XZ/YZ, max/min/mean, dtypes, NaNs, anisotropy, signed axis permutations, boundaries and subvoxel slabs. Integer extrema exact; mean tolerances explicitly documented. Existing oblique 2D rejection remains tested. |
| Async correctness | Rapid 100-request scrub displays the last request; old results cannot reappear after source replacement, layer removal, quality change or viewer close. Authored visibility and managed layer IDs remain intact. |
| Export correctness | No stale, duplicated or reordered frames with async slicing enabled; slow/failed writer and cancellation leave the GUI responsive and restore the original scene. Compare exported frames to deterministic synchronous references. |
| Backend selection | Compare warmed NumPy/Numba/CUDA at matched quality including I/O and transfers, not only kernels. Enable a default accelerated path only when its representative end-to-end benefit is clear (suggested gate: at least 20%) without harming GUI latency or correctness. |
| Resource limits | Record peak process RSS, device allocations and actual GPU memory use; stay within configured cache/in-flight budgets; no unbounded growth on prolonged scrubbing. Missing CUDA, incompatible runtime and OOM fall back cleanly. |

The benchmark matrix should include the supplied IMS fixture, a large representative IMS, a flat Luxendo file, a multi-file external-link acquisition, multiple channels/timepoints, local SSD versus the actual storage path, native compression/chunk variants, warm/cold application caches, three orthogonal views, thin/thick slabs, and 2D/3D transitions. Application-cache cold is not necessarily OS-disk-cache cold; record that distinction. Run existing renderer, ortho-slice, prefetch and export regression tests after the relevant implementation phases, and add meaningful cancellation/numerical/resource tests rather than tests that merely mirror new code.

Recommended delivery order: baseline and redundant-binding fix; asynchronous projections plus corrected prefetch/cache; progressive Imaris/Luxendo loading; Numba reductions; measured CUDA prototype; event-driven export (which can be developed independently once request readiness is defined). The first three deliveries address the strongest explanations for multi-second button freezes. CUDA remains a targeted compute optimization, with a decision gate based on actual measurements.
